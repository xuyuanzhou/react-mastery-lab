# 48. React 行为测试与可访问性验收

> 理解内部机制还不足以证明应用正确。要能把“用户会怎样操作和观察”变成可重复的测试，并区分 React 更新、浏览器行为与开发模式检查。本章与[工程实践的质量检查](../engineering/03-质量检查与发布.md)配合使用。

## 学习目标

能为状态身份、表单、Effect 清理、异步边界和错误恢复写行为级测试；能用标签、语义角色、键盘和焦点检查基本可访问性；不会用内部函数调用次数代替用户结果。

## 1. 测什么：公开行为优先，内部实现用于诊断

下面两种断言强度不同：

```text
弱：Counter 函数刚好调用了 2 次。
强：用户点击“增加”后，页面上的数字从 0 变 1；换 key 后重置为 0。
```

开发环境 StrictMode、并发重试和实现优化会改变 Render 次数，因此函数调用次数通常不能当公共行为契约。先测用户可见结果，再用 Profiler、断点和源码解释失败。React 的 [act](source:packages/react/src/ReactAct.js#act) 帮助测试环境把相关更新推进到可断言的状态；具体测试工具可能已为用户操作封装了它，不要机械地给每行代码再套一层。

## 2. 一个完整的状态身份测试

假设表单组件 `<Editor key={selectedId} />`，用户在 A 项输入草稿后切换到 B。测试应覆盖：

1. A 的输入框有可访问的名称，例如 `<label htmlFor="draft">草稿</label><input id="draft" />`。
2. 通过输入框的角色与名称找到它，而不是靠 CSS 类名或 DOM 下标。
3. 输入文本、切换 B，断言 B 的草稿是初始值；切回 A 是否恢复，取决于业务是否把草稿放在更高层或外部 Store。不能只凭 key 推断跨卸载的数据持久化。
4. 把 key 固定不变，再验证状态是否保留，从而用对照实验说明身份差异。

React 层原因在 [Reconciliation](source:packages/react-reconciler/src/ReactChildFiber.js#reconcileChildFibers) 与 [Hook 更新](source:packages/react-reconciler/src/ReactFiberHooks.js#updateState)；测试只写产品可观察结论，源码用于解释。

## 3. Effect 与异步边界的测试

对订阅组件，记录 `subscribe(roomId)` 与清理函数。先 Mount A，再切 B，再 Unmount；断言旧 A 被清理、B 被建立、最终 B 也被清理。若在 StrictMode 下观察到额外 setup/cleanup，应检查逻辑在重放后是否仍正确，而不是用 ref 阻止第二次运行。

对 Suspense，测试“资源 pending 时显示 fallback、完成后显示数据”；对 Error Boundary，测试 rejection/error 是否进入错误 UI。不要用固定毫秒的 sleep 猜测内部调度。Hydration 还要单独验证服务端 HTML 与客户端初始输出一致；[hydrateRoot](source:packages/react-dom/src/client/ReactDOMRoot.js#hydrateRoot) 与普通 `createRoot` 的前提不同。

## 4. 基本可访问性不是最后的装饰

```tsx
<label htmlFor="search">搜索商品</label>
<input id="search" value={query} onChange={event => setQuery(event.target.value)} />
<button type="submit">搜索</button>
```

有标签的控件更容易被屏幕阅读器理解，也让测试能按角色与名称定位。交互组件还应检查 Tab 顺序、Enter/Space 操作、焦点是否被弹窗正确管理、错误提示是否可被感知。React 负责生成和更新 DOM；语义正确性仍由应用作者设计。不要用 `<div onClick>` 替代原生按钮，除非同时承担完整键盘与语义行为。

## 5. 分层测试策略

| 层 | 例子 | 主要证明什么 |
|---|---|---|
| 纯函数 | reducer、筛选函数 | 输入输出和边界值 |
| 组件行为 | 表单输入、key 重置、Effect 清理 | 用户交互与 React 状态结果 |
| 浏览器集成 | 焦点、布局、真实 Paint、Hydration | DOM/浏览器环境中的行为 |
| 源码实验 | 断点跟踪 Hook Queue 或 Lane | 固定版本内部机制 |

纯函数和 DOM 模拟环境不能证明真实浏览器绘制或键盘焦点的所有细节；源码断点也不能代替业务可用性测试。选择最便宜但足以证明问题的层，再升级到浏览器集成。

## 动手实验

给[Mini React 的行为测试](project:mini-react/test/runtime.test.mjs#L1)补一个 key 重排案例；再在本站工程加一个带标签的输入控件，用项目现有的测试工具按角色与名称查找、输入和断言。最后在浏览器中只用键盘操作一次，记录焦点位置。对每个失败写清“用户结果错误、DOM 语义错误，还是内部假设错误”。

## 自检

1. 测试只断言“组件函数执行两次”，能证明点击后正确吗？为什么？
2. 为什么 `getByRole('button', { name: '保存' })` 通常比 `.save-button` 更适合作为行为测试入口？它能代替全部可访问性检查吗？
3. `useEffect` 订阅在 StrictMode 下出现 setup → cleanup → setup，应改成“只允许第一次 setup”吗？

## 参考答案

1. 不能。Render 可重做或被开发模式额外调用，且一次 Render 未必 Commit。应触发点击并断言屏幕状态、必要的业务副作用，再在需要时用 Profiler/源码解释次数。
2. 角色和可访问名称对应用户能感知的控件语义，CSS 类名只是实现细节；但这不能证明键盘顺序、焦点、对比度和辅助技术体验，仍需实际检查。
3. 不应靠 ref 屏蔽检查。正确订阅必须让 cleanup 撤销旧 setup，重复建立后只留下当前有效订阅。若有重复请求或泄漏，应修复资源生命周期，而不是隐藏开发模式信号。
