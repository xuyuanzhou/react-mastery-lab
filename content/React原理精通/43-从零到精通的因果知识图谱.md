# 43. 从零到精通的 React 因果知识图谱

这不是目录，而是“为什么下一章必须建立在上一层之上”的因果图。

```text
JavaScript 闭包 / 调用栈
        ↓
函数组件 Render Snapshot（渲染快照）
        ↓
为什么状态不能存在函数局部变量里
        ↓
Fiber + Hook 链表
        ↓
为什么 Hook 依赖固定顺序
        ↓
Update / UpdateQueue
        ↓
为什么 setter 不是直接赋值
        ↓
Lane（更新优先级集合）
        ↓
为什么 Queue 需要 baseState/baseQueue 做 Rebase（重基）
        ↓
Root Scheduler（根调度器）
        ↓
Render WorkLoop（渲染工作循环）
        ↓
beginWork / Reconciliation（协调）
        ↓
completeWork / flags（副作用标记）
        ↓
Commit（提交）
        ↓
Renderer / DOM mutation（DOM 变更）
        ↓
Browser Style/Layout/Paint/Composite
```

另一条并发主线：

```text
JS 主线程有限
↓
同步递归工作不可让位
↓
Stack Reconciler 的架构约束
↓
Fiber 将工作显式化
↓
可暂停 Render
↓
Lane 表达不同优先级工作
↓
Transition / Deferred / Suspense
↓
并发一致性、Tearing、External Store
```

另一条服务端主线：

```text
CSR 首屏成本
↓
SSR 输出 HTML
↓
Hydration 复用服务端 DOM
↓
Streaming + Suspense
↓
Selective Hydration（选择性水合）
↓
RSC / Flight（服务器组件协议）
```

学习时遇到不懂的概念，应沿箭头回退一层，而不是继续硬读源码。

## 根据“卡住的现象”回退，而不是从头重读

| 卡住的问题 | 先补哪一层 | 再回到哪一章 |
|---|---|---|
| 为什么条件里的 Hook 会错位？ | 链表、调用顺序、Render Snapshot | [Hook Dispatcher 与链表](03-Hooks-Dispatcher与链表.md) |
| 为什么跳过低优先级更新后还要重放？ | 队列顺序、函数复合 | [useState 与 UpdateQueue](04-useState与UpdateQueue.md) |
| 为什么 `setState` 后 DOM 不一定立刻变？ | Event Loop、Render/Commit、浏览器绘制 | [完整 setState 调用链](10-完整setState调用链.md) |
| 为什么 HTML 已出现，点击还可能等一会儿？ | SSR、Hydration cursor、boundary | [SSR 与 Hydration](15-SSR与Hydration.md) |

**自检：** 能否从“输入卡顿”反向找到三种不同原因？**参考解析：** 可能是组件中的长同步计算没有让位、同一紧急 Lane 的工作过多，或者 React 已提交但浏览器 Layout/Paint 昂贵。先用 Performance 时间线区分 JavaScript 与渲染流水线，再决定是拆分计算、降低非紧急更新优先级，还是优化 DOM/CSS。只说“加 `useMemo`”不足以诊断。
