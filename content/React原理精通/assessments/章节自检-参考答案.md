# React Mastery 章节自检：参考答案与验收标准

> 本文件对应各章节末尾的“自检”。建议先脱稿回答，再来核对。

## 00B：JSX / Element / Fiber / Host Instance

### 为什么 JSX 创建了新对象，组件 state 却可能保留？

JSX 每次执行产生新的 React Element 描述，但 Reconciler 会根据同一父级中的 `key/type/结构位置` 匹配旧 Fiber。匹配成功时复用 Fiber identity，因此 Hook/Class state 可从 current Fiber 延续；Element 对象本身不承载长期 state。

### 为什么函数组件没有 instance 仍能有 state？

因为 state 存在 `FunctionComponent Fiber.memoizedState` 指向的 Hook 链表与 UpdateQueue 中，不存在函数对象上。

### 为什么 React 可以支持非 DOM renderer？

Reconciler 不直接依赖 `document.createElement`；宿主行为通过 Host Config/Renderer 注入。Fiber、Hooks、Diff、调度大多平台无关。

### 为什么 key 改变会重置 state？

key 属于 child identity。key 改变时新 child 无法匹配旧 Fiber，旧 Fiber 删除，新 Fiber mount，Hook state 从初始化值重新创建。

## 13：React 事件系统

### 1. 为什么 DOM 节点必须能反查 Fiber？

Native event 首先只给浏览器 target DOM。React 要恢复组件语义：找到最近 Host Fiber，再沿 Fiber return 链收集对应 props listener、处理 Portal/Root 边界、分配 update priority。DOM→Fiber 映射是事件系统从“宿主对象”回到“React Tree”的入口。

### 2. root delegation 相比 document delegation 解决了什么架构问题？

Root 级 delegation 让多个 React root、不同 React 版本、嵌入式应用拥有更明确的事件边界，减少所有 React app 共用 document 全局 listener 的耦合。它也更容易把事件传播与具体 root container 对齐。

### 3. Portal 为什么能证明 React propagation 不只是 DOM `parentNode` traversal？

Portal 的 DOM child 可以挂在另一 DOM container，但 Fiber `return` 仍属于原 React parent。React 合成事件能按 React component tree 传播到逻辑父组件，说明 listener 收集依赖 Fiber ancestry，而不是简单沿 `event.target.parentNode`。

### 4. `nonDelegatedEvents` 为什么存在？

某些原生事件不可靠冒泡、具有特殊浏览器语义，无法仅靠 root 上的冒泡委托覆盖，所以 React 需要直接在目标元素/特殊节点监听。这是宿主事件能力差异，不是合成事件设计失败。

### 5. 一次 click 中 `setState` 的 lane 从哪里获得优先级信息？

`ReactDOMEventListener` 根据 native event 选择 `Discrete/Continuous/DefaultEventPriority`，事件 wrapper 在 dispatch 时设置 current update priority。随后 state setter 调用 `requestUpdateLane` 时读取当前 transition/update priority，并映射到对应 Lane。

## 14：Suspense

### 1. 为什么使用 opaque `SuspenseException`？

避免真实 thenable 被用户 `try/catch` 当业务对象捕获，同时把 suspension 保持为 React 私有控制流协议；真实 thenable 暂存在 `suspendedThenable`，WorkLoop 通过 `getSuspendedThenable()` 读取。

### 2. 为什么 thenable resolve 只能触发 retry，不能直接 mutate DOM？

thenable resolve 只说明依赖可能可读了，组件的下一 UI 仍必须重新执行 Render、通过 reconciliation 得到一致候选树，并经 Commit 原子应用。直接改 DOM 会绕过 Fiber identity/state/effect/error 体系。

### 3. 为什么 Suspense 依赖 current/WIP？

尝试 primary tree 时可能 suspend。React 必须在不破坏当前已提交 UI 的情况下放弃/重做候选、改 render fallback、或 transition 中保留旧 UI。current/WIP 隔离正好提供这个能力。

### 4. Transition + Suspense 为什么能避免已有 UI 立即闪成 fallback？

Transition 更新被标记为非紧急 lane。若候选 UI suspend，React 可以继续保留 current UI，同时等待 transition/资源完成，而不是像 urgent update 那样必须尽快提交新的 fallback；具体策略还受 boundary 和 timeout/heuristics 影响。

### 5. Server Streaming 为什么把 Suspense boundary 当关键单元？

Boundary 定义了可独立等待、fallback、后续补发内容的切分点。Fizz 可以先发送 shell/fallback，再在 boundary 完成后把对应 segment 流式发送并在客户端替换/协调。

## 15：SSR / Hydration

### 1. 为什么 hydration 必须有 cursor，而普通 mount 不需要？

Mount 没有旧 DOM 要复用，Renderer 可直接创建节点。Hydration 必须把 Fiber DFS 顺序与现有服务器 DOM 的“下一个可认领节点”对齐，因此需要 hydration parent / next hydratable instance 等 cursor 状态。

### 2. 为什么 HTML 已可见不代表页面已可交互？

SSR HTML 只有 DOM 结构；React 事件系统、Fiber、client state、effect、模块代码可能尚未加载/执行。Hydration 完成相关 boundary 前，用户看到的是“可见但未完全接管”的 UI。

### 3. Event Replay 与 Selective Hydration 为什么必须配合？

用户可能在尚未 hydrated 的 boundary 上点击。React 可以识别事件被 dehydrated boundary 阻塞，提高该 boundary hydration 优先级，并暂存/重放合适事件，避免“必须从页面顶部顺序 hydration 完才响应”。

### 4. `useId` 为什么不能简单用 `Math.random()`？

Hydration 要求服务器和客户端第一次 render 生成相同 ID，否则属性/关联关系 mismatch。随机数无法确定性重现；`useId` 使用树位置/identifier prefix 等确定性机制以跨 server/client 对齐。

### 5. Fizz 与 RSC 分别传输什么？

Fizz 是 React 的 streaming SSR renderer，核心输出 HTML/用于 streaming boundary 的脚本/指令；RSC/Flight 传输的是序列化 React 模型、Client/Server references、模块引用和值。二者可组合但协议目标不同。

## 16：Class 生命周期与 Fiber

### 1. Class instance 为什么持久存在，但 render 仍必须纯？

持久 instance 只是 state/method 容器；Fiber Render 仍可能重试、并发重做或因为 error/suspense 放弃。若 `render()` 修改外部世界，重放次数就会改变外部结果，因此 Render purity 与有没有 instance 无关。

### 2. `this.setState` 与 Hook `setState` 的共同架构原则是什么？

都不是“立即改当前渲染中的变量/DOM”，而是创建/入队 Update、选择 lane、向 Root 调度下一次 Render。状态最终在 Render 中消费队列后得到新 snapshot。

### 3. `getSnapshotBeforeUpdate` 为什么必须在 mutation 之前？

它的用途正是读取“旧 DOM 即将被 React 修改前”的信息，例如滚动高度。Mutation 后旧布局已经丢失，因此必须在 before-mutation window 读取，再把 snapshot 传给 `componentDidUpdate`。

### 4. UNSAFE lifecycle 的真正问题是什么？

不是名称过时，而是它们常发生在 Render 侧、开发者又习惯做副作用；可重放/可中断 Render 下可能调用多次或最终不 Commit，与外部副作用语义冲突。

### 5. 为什么不能用 Class lifecycle 机械解释 Hooks？

Effect 的模型是“某段外部同步的建立与 cleanup”，由 dependencies 决定重新同步；一个组件可以有多个独立 effects。它不等价于把 `componentDidMount/componentDidUpdate/componentWillUnmount` 一一改名，而且 Function Component 还有 render snapshot/closure 语义。

## 19：Error Boundary 与错误恢复

### 1. 为什么 Render error 更容易通过重新 render recovery？

Render 尚未向 Host Tree 提交副作用，候选 WIP 可以丢弃；React 找到可处理 Error Boundary，给它入队 captured update，再从安全位置重新 render fallback。

### 2. 为什么 Commit error 不能简单 rollback DOM？

Commit 可能已经执行部分 DOM mutation、ref、layout effect 和用户代码。DOM API 不是 React 的事务日志，外部副作用也未必可逆，因此“把 Fiber 指针切回去”并不能恢复所有外部世界。

### 3. Suspense pending 和 rejected 为什么进入不同 boundary？

Pending thenable 是“当前还没有值”的控制流，应该由 Suspense boundary 处理并等待 retry；rejected thenable/普通 Error 是失败，应该进入 Error Boundary/错误恢复路径。两者代表不同 UI 语义。

### 4. 为什么 Event handler error 不等价于 child render error？

Error Boundary 捕获的是 React 正在执行 descendant render/lifecycle/commit 等受控树工作中的错误。事件 handler 是已经 Commit 后由用户交互触发的命令式回调，错误不会通过“重新 render 该 child”自然恢复；应用需在 handler 自己处理或触发 state 表示错误。

## 20：Server Components / Flight

### 1. RSC payload 为什么不能叫 HTML？

它编码 React 模型和值/引用关系，可包含 ClientReference、ServerReference、Promise/chunk、序列化 props 等；客户端 Flight runtime 解析后得到可继续参与 React rendering 的模型，不是浏览器直接解析的 DOM markup。

### 2. `'use client'` 为什么是模块图边界？

一旦 Server Component import 一个带 `'use client'` 的模块，bundler 把该模块及其传递依赖作为客户端模块图的一部分，并在 Server graph 中用 Client Reference 表示。它影响编译/打包，不是运行时 `if (isBrowser)`。

### 3. Server Component 引用 Client Component 时服务器传什么？

服务器不会把 Client Component 函数实现序列化过去，而是发送 Client Reference（模块/导出标识）以及可序列化 props/children。客户端 bundler/runtime 根据 reference 加载真正模块。

### 4. RSC + SSR 为什么可以同时存在？

RSC 解决“哪些组件在哪里执行、传输什么 React model”；SSR/Fizz 解决“如何把最终可渲染树转成首屏 HTML 并流式输出”。框架可以先产生 RSC model，再用它参与 SSR HTML，同时把 Flight payload 给客户端后续导航/更新。

### 5. Server Action 为什么更像 RPC capability？

客户端拿到的是服务器函数 reference/capability，可以通过框架协议调用；参数/返回值跨网络序列化，实际代码仍在服务器执行。它的调用语义比普通本地函数更接近 RPC。

## 21：useSyncExternalStore / Tearing

### 1. 为什么简单 `useEffect(subscribe)` 有一致性窗口？

Render 可以先读 store 版本 A，但 Commit/useEffect subscribe 前 store 已变成 B；如果变化发生在订阅生效前，通知可能丢失。Concurrent render 还可能跨多个时间片读到不同版本。官方协议需要 snapshot 校验来关闭这类窗口。

### 2. `getSnapshot` 为什么不能每次返回新对象？

React 用 `Object.is` 判断 snapshot 是否变化。若 store 未变化却每次创建 `{...}`，React 会认为持续变化，造成不必要更新甚至循环。应返回缓存的不可变 snapshot，只有底层 store 版本变化才换引用。

### 3. React 自己的 `useState` 为什么较少面临同样 tearing 问题？

内部 state update 被纳入 Fiber/Lane/UpdateQueue，某次 render 使用的是一组确定 render lanes 下的 state snapshot；React 可以控制 current/WIP 与 commit 边界。外部 store 则能在 React 不知情时随时 mutation，所以需要额外协议。

### 4. `getServerSnapshot` 与 hydration 有什么关系？

Hydration 的客户端第一次 render 必须看到与服务器 HTML 对应的同一 snapshot，即使真实 store 已在服务器响应后变化。`getServerSnapshot` 提供该“服务器版本”，hydration 完成后再切到客户端 `getSnapshot` 并处理变化。

## 22：Host Config / 自定义 Renderer

### 1. 为什么 HostComponent `stateNode` 对 DOM renderer 是 DOM node，而 FunctionComponent 不是？

HostComponent 正对应宿主环境实体，Renderer 必须保存真实 instance 供 Commit 更新；FunctionComponent 只是 React 计算单元，没有天然宿主对象，它的持久状态放 Fiber/Hooks。

### 2. `completeWork` 中创建 DOM 为什么仍可以属于 Render Phase？

“创建未挂载 DOM object”本身通常对用户不可见。React 可以在 WIP 中预创建 instance，但不把它插入当前 container；若 Render 被丢弃，这些 detached nodes 可被 GC。真正让外部 Host Tree 可见的 insert/update/delete 在 Commit。

### 3. Host Config 属于什么设计思想？

Dependency inversion + Adapter/Strategy：Reconciler 定义需要哪些宿主能力，Renderer 提供具体实现，使核心算法与 DOM/Native/Canvas 解耦。

### 4. 为什么自定义 Renderer 能纠正“Virtual DOM = DOM wrapper”？

同一 Fiber/Reconciler 可以驱动完全不是 DOM 的 host instance，说明 React 的虚拟表示是“UI/组件工作模型”，DOM 只是一个 Renderer target。

## 23：React Compiler

### 1. 为什么需要自己的 IR？

安全自动 memo 需要统一表达控制流、依赖、值生命周期、alias/mutation，并执行多轮分析/转换；直接在 JSX AST 上局部模式匹配无法可靠推导这些语义。

### 2. 自动 memo 为什么依赖 Render purity？

若某表达式每次执行都会产生外部副作用，Compiler 将它缓存并跳过执行会改变程序行为。只有可重放/pure 的 render 计算才能安全做等价消除与复用。

### 3. 为什么 Compiler 不是“自动包 React.memo”？

它可以在组件内部建立更细粒度缓存单元，缓存值、JSX、闭包或依赖计算，并利用数据流分析决定复用范围；这比组件级 props shallow compare 粒度更细。

### 4. 为什么不能解决 layout thrashing？

Compiler 优化 React/JS render 计算和引用稳定性；layout thrashing 是浏览器因 DOM read/write 顺序导致的同步 style/layout 问题，属于 Host pipeline，需要改变 DOM 操作模式/Effect/样式策略。

## 24：StrictMode / Rules of React

### 1. 为什么“生产不重复”不能成为写不纯 Render 的理由？

StrictMode double render 是帮你暴露真正的架构错误。即使生产不做相同 DEV 检查，Concurrent interruption、Suspense/error recovery、未来优化仍可能让 Render 重试或放弃。不纯 Render 从模型上就是不安全。

### 2. StrictMode 为什么与 Concurrent Render 的可重放哲学一致？

它主动模拟“render/effect 可能再次执行”的环境，逼迫代码满足可重放性和 cleanup 对称性，这正是可中断/可恢复架构需要的性质。

### 3. Effect double-connect 暴露的是哪类 bug？

通常是 cleanup 不完整或 effect 并非幂等：第一次 connect 后 cleanup 没有真正 disconnect，第二次 mount 再 connect 形成重复订阅、重复 timer、重复 observer 等资源泄漏。

## 25：Profiler / 性能工程

### 1. 为什么 React Profiler 不能代替 Browser Performance？

Profiler 聚焦 React render/commit；Browser Performance 才能看到事件延迟、Long Task、非 React JS、Style/Layout/Paint/Raster/Composite、GC 等从输入到像素的完整主线程成本。

### 2. 为什么 `useMemo` 不能修复 Layout？

`useMemo` 只减少某个 React render 计算；如果卡顿来自 DOM 尺寸变化、强制同步布局或昂贵 paint，缓存 JS 值不会改变浏览器 layout pipeline。

### 3. key 不稳定会怎样同时伤害 Render 与 Commit？

Render 侧：Reconciler 无法复用旧 Fiber/Hook state，产生更多 mount/unmount/子树工作；Commit 侧：更多 Placement/Deletion、ref/effect cleanup/setup、DOM 创建删除，因此双重放大成本。

### 4. Compiler 自动 memo 后为什么仍需要架构级性能设计？

数据获取、列表虚拟化、状态粒度、Context fan-out、网络 waterfall、DOM 数量、图片、布局、动画、服务端策略都不是自动 memo 能解决的。性能仍是端到端系统属性。

## 26：Ref / ImperativeHandle

### 1. `useRef` 为什么不触发 render？

ref 是一个持久 mutable cell，修改 `ref.current` 不创建 Update、不分配 Lane、不调用 scheduleUpdateOnFiber；它用于不参与 UI 声明式计算的数据。

### 2. 为什么 host ref attach 必须在 Commit？

只有 Commit 后 Host Instance 才代表真正已提交树；Render 候选可能丢弃。若提前赋值，用户会拿到未提交 instance。

### 3. `useImperativeHandle` 解决的是状态问题还是封装问题？

主要是**命令式能力封装/API surface**：父组件拿到的不是整个内部 DOM，而是子组件显式暴露的 handle。它不替代 state，也不应作为普通数据流工具。

### 4. Fragment refs 为什么证明 ref 不必等于单 DOM node？

ref 的抽象本质是“提交后暴露的命令式 handle”，可以是 DOM node、Class instance、自定义 object，或某种 Fragment handle。它的语义由组件/Renderer定义，不等于“永远一个 HTMLElement”。

## 27：Batching / flushSync

### 1. 为什么 batching 后 UpdateQueue 仍要保存多个 Update？

Batching 只表示“多个 Update 可以共享一次 render/commit 时机”，不表示它们逻辑上合并成一个 action。每个 updater 的顺序、lane、函数式计算都必须保留，Render 时逐个消费。

### 2. 三次 `setCount(count + 1)` 只 +1 与 batching 的真正关系是什么？

根因是三次调用都捕获同一 render snapshot 的 `count`，所以 action 都是“替换为 1”。Batching 让它们通常在同一 render 里一起处理，但即使逐次排队，三个 replace(1) 的逻辑结果仍不会自然变成 +3。函数式 `c => c + 1` 才表达连续状态转移。

### 3. Root microtask 为什么有助于 batching，但 batching 又不等于 microtask？

把 Root 真正调度决策推迟到 microtask，可聚合同一浏览器 task 内多次 updates 后统一处理，因此有助于自动 batching。但 batching 是 React 的更新语义/调度策略；React 可以在不同执行上下文批处理，microtask 只是当前 Root Scheduler 实现的重要机制之一。

### 4. `flushSync` 为什么是 escape hatch？

它要求 React 放弃部分并发/批处理自由，在函数返回前同步完成相关 DOM commit，以满足测量/第三方 API 等“现在就必须看到 DOM”的需求。频繁使用会造成主线程阻塞、额外 commit、破坏 transition/Suspense 体验，因此只应解决无法通过正常声明式时序表达的边界需求。
