# 10. 性能基础：Main Thread、Frame Budget 与长任务

> 目标：理解 React 为什么要做可调度的 Render。Fiber 的价值只有放在浏览器主线程约束下才真正容易理解。

## 1. 浏览器主线程很忙

主线程通常同时承担：

```text
JavaScript
Style Calculation
Layout
部分 Paint 工作
事件回调
```

如果一段 JavaScript 长时间占住主线程，用户输入、滚动与下一帧绘制都会被延迟。

## 2. Frame（帧）预算

60Hz 屏幕大约每 16.7ms 出现一次刷新机会，但这 16.7ms 不是“JavaScript 可以独占的时间”。浏览器还要完成样式、布局、绘制与其他工作。

因此真正应该关注的是：

- Long Task（长任务）是否阻塞主线程；
- 一次更新是否触发不必要的 Layout/Paint；
- React Render 工作能否分段并让更紧急任务优先；
- Commit 中同步工作是否过重。

## 3. React Render 和 Browser Paint 不是一回事

```text
React Render Phase
计算下一棵 Fiber Tree
        ↓
React Commit Phase
修改 DOM / ref / effects
        ↓
Browser Rendering Pipeline
Style → Layout → Paint → Composite
```

React 可以优化“算什么、什么时候算、DOM 改多少”，但最后的像素仍由浏览器渲染管线产生。

## 4. 为什么 transform/opacity 动画经常更平滑

很多情况下它们更容易避免 Layout，甚至避免重新 Paint，把更多工作留给 Composite；而频繁修改 `width/height/top/left` 可能让浏览器重新布局。

这不是绝对规则，必须以 DevTools Performance/Profile 测量为准。
